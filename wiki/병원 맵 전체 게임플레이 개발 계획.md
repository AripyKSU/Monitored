# 병원 맵 전체 게임플레이 개발 계획

## 1. 문서 목적

현재 완성된 병원 맵과 기존 게임 시스템을 기반으로, 게임 시작부터 최종 추격 및 엔딩까지 남아 있는 기능을 단계별로 구현한다.

이 문서는 각 단계를 GPT/Codex에게 독립적으로 전달해도 구현할 수 있을 정도의 명세를 목표로 한다.

이미 구현이 완료된 시스템은 다시 만드는 작업에 포함하지 않는다. 대신 새 기능에서는 가능한 한 기존 시스템을 재사용하거나 확장한다.

---

# 2. 기본 개발 원칙

## 기존 시스템 우선 사용

작업을 시작하기 전에 현재 구현을 확인하고 다음 시스템을 우선 활용한다.

- `GameSession`
- `CheckpointService`
- `CheckpointResolver`
- `RespawnCoordinator`
- `PlayerRoomTracker`
- 기존 Door / Room 이동 시스템
- 기존 Target / TargetPresenter 계열 상호작용 시스템
- 기존 `MessageTarget`
- 기존 `ItemAcquired` 계열 아이템 획득 시스템
- 기존 Inventory / Item Use UI
- 기존 Hide / Stealth 시스템
- 기존 Enemy AI 및 추적 시스템
- 기존 `DialogueService`
- 기존 `DialoguePresenter`
- 기존 `DialogueView`

같은 기능의 시스템을 새로 병렬 구현하지 않는다.

기존 코드가 필요한 기능을 거의 제공하고 있다면 작은 확장을 우선한다.

# 3. 전체 진행 구조

게임 진행을 다음 5개 체크포인트 구간으로 나눈다.

```text
Save1
Sector1
병실 구역 탐색
↓
병실 복도 열쇠 획득
↓
Center Hallway 첫 번째 구역 진입

Save2
Sector2
퓨즈 → 발전기 → 기계실 → 철창 해제
↓
살인마 숨기 이벤트
↓
Center Hallway 두 번째 구역 진입

Save3
Sector3
살인마 패트롤 시작
↓
식당 힌트
↓
주방에서 지하 통로 열쇠 획득
↓
지하계단 진입

Save4
Sector4
지하 구역 살인마 패트롤
↓
살인마 일기 3 획득
↓
시체안치함 B 조사
↓
마스터키 획득

Save5
Sector5
지하계단 접근
↓
최종 추격 시작
↓
정문 도착
↓
MonitoringRoom → Bad Ending
또는
숨겨진 정문 Target → Happy Ending
```

체크포인트는 **현재 플레이 세션 동안만 유지되는 인메모리 체크포인트**다.

WebGL의 영구 저장은 이번 개발 범위에 포함하지 않는다.

# 4. Story Progress 상태 관리

## 목적

씬 오브젝트의 단순 `SetActive` 상태만으로 스토리를 관리하지 않는다.

체크포인트 복원과 일회성 이벤트 판정을 위해 명시적인 진행 상태를 둔다.

기존 `GameSession` 구조와 연결되는 별도 Story Progress 상태를 두는 것을 권장한다.

예시 클래스명:

```text
StoryProgressService
```

실제 프로젝트에 동일 역할 시스템이 존재하면 그것을 확장한다.

---

## Story Stage

큰 진행 단계는 하나의 단계 값으로 관리한다.

예:

```text
Sector1
Sector2
Sector3
Sector4
Sector5Ready
FinalChase
Ending
```


필요하다면 기존 시스템 명명 규칙에 맞추어 이름을 변경해도 된다.

---

## 상태 변경 규칙

Story Flag 변경 시 필요한 오브젝트들이 직접 상태 변경 이벤트를 받아 처리하도록 한다.

씬 전체를 순회하여 모든 Target을 찾아 활성화/비활성화하는 구조는 사용하지 않는다.

예:

```text
FreezerHintRead
    ↓
주방 열쇠 냉장고 Target 활성화

KillerDiary3Read
    ↓
Morgue Box B 추가 상호작용 활성화
```

# 5. Dialogue 작성 규칙

현재 단계에서는 실제 스토리 문장을 작성하지 않는다.

스토리 대사가 필요한 곳에는 다음과 같은 placeholder를 넣는다.

```text
[게임 시작 무전기 대화]

[복도 끝 문이 닫히는 것을 본 주인공]

[중앙 복도 철창 발견]

[빨리 숨어야 한다]

[살인마가 돌아다니고 있으니 조심해야 한다]

[이 문이 출구이며 마스터키가 필요하다]

[일기장 1번]

[식당 힌트보드]

[일기장 2번]

[살인마 일기 3번]

[생존자의 메시지]

[마스터키 획득 후 무전기]

[도망쳐]

[왼쪽 방]

[Bad Ending 텍스트 대체본]

[Happy Ending 텍스트 대체본]
```

각 스토리 기능을 구현한 뒤 반드시 사용자에게 해당 placeholder 목록을 알려 실제 문구를 넣어야 할 위치를 전달한다.

---

## Dialogue Pause 규칙

기본 Story Dialogue는 Pause 상태로 실행한다.

Pause 상태에서는 최소한 다음이 정지해야 한다.

- 플레이어 상호작용
- 플레이어 이동 명령
- 일반 Enemy AI
- 스토리 진행 입력

특별히 명시한 Dialogue만 Non-Pause로 실행한다.

대표적인 예:

```text
Sector5 정문 도착 후
[왼쪽 방]
```

이 메시지는 최종 추격이 계속되는 동안 표시한다.

# 6. Checkpoint 정의

## Save1

### 생성 시점

게임 최초 시작.

### 위치

`Sector1/StartBedroom`

기존 `StartBedroomPoint` 또는 그 역할을 하는 Spawn Transform을 사용한다.

### 복원 상태

- Story Stage = Sector1
- Intro 미완료
- Enemy 비활성
- 시작 발밑 Target만 활성
- 다른 StartBedroom Target 비활성

---

## Save2

### 생성 시점

병실 복도 열쇠를 사용해 Sector1을 빠져나온 뒤 **Center Hallway 첫 번째 논리 구역에 처음 진입했을 때**.

### 복원 상태

- 병실 복도 열쇠 보유
- Sector1 주요 진행 완료
- 해당 문 다시 통과 가능
- Center Hallway 첫 번째 구역에서 시작
- 철창 닫힘
- Sector2 진행 미완료

---

## Save3

### 생성 시점

다음 조건이 모두 끝난 뒤:

1. 발전기 작동
2. 기계실 장치 작동
3. 철창 해제 연출
4. EnemySpawnRoom의 살인마 등장
5. MachineRoom 숨기 이벤트 완료
6. 살인마 퇴장
7. 플레이어가 다시 방을 나옴
8. **Center Hallway 두 번째 논리 구역에 처음 진입**

### 복원 상태

- 철창 통과 가능
- Sector2 강제 숨기 이벤트 재생 금지
- 발전기/기계 상태 완료
- Sector3 살인마가 DiningRoom 패트롤 시작 위치에서 초기화
- Center Hallway 두 번째 구역에서 시작

---

## Save4

### 생성 시점

지하 통로 열쇠로 계단을 통과하여 **BasementCorridor에 처음 진입했을 때**.

### 복원 상태

- 지하 통로 열쇠 보유
- Sector3 진행 완료
- Sector4 살인마 패트롤 활성
- 살인마 패트롤 시작점 = MorgueRoom2
- BasementCorridor에서 시작

---

## Save5

### 생성 시점

MorgueRoom2의 시체안치함 B에서 마스터키를 획득하고,

```text
[마스터키 획득 후 무전기]
```

Dialogue까지 완료한 시점.

### 복원 상태

- 마스터키 보유
- KillerDiary3Read 유지
- MasterKeyAcquired 유지
- Sector4 진행 상태 유지
- FinalChaseStarted = false
- 최종 추격은 아직 시작하지 않음

Sector4 살인마는 기존 체크포인트 Enemy 복원 방식을 사용한다.

Save5 재시작 직후 플레이어와 살인마가 겹치거나 즉시 사망하는 문제가 발생한다면 별도의 안전한 Enemy Restore Point를 지정한다.

# 7. 아이템 유지 규칙

## 영구 보유

다음 아이템은 획득 후 사용해도 제거하지 않는다.

```text
손전등
병실 복도 열쇠
지하 통로 열쇠
마스터키
```

특히 열쇠 아이템은 체크포인트 복원 이후 문 상태와 아이템 상태가 불일치하더라도 다시 문을 열 수 있도록 유지한다.

---

## 소비 아이템

```text
퓨즈
```

퓨즈는 발전기에 정상 설치된 순간 소비한다.

잘못된 상호작용으로는 소비하지 않는다.

# 8. Scene Hierarchy 정리

실제 기능 구현 전에 명백한 임시 이름들을 정리한다.

예:

```text
Sector5/ZeopSu
→ Sector5/Reception

Sector5/Door
→ Sector5/Entrance
```

`Hallway (1)`처럼 의미가 명확한 임시 이름도 가능한 범위에서 역할 기반 이름으로 정리한다.

예:

```text
Sector3/Hallway (1)
→ Sector3/ServiceHallway
```

단, 이름 변경 전에 해당 경로를 문자열로 참조하는 코드가 있는지 검사한다.

코드에서 이름 기반 `GameObject.Find` 등을 사용하고 있다면 먼저 참조 구조를 안전하게 변경한다.

# 9. 공통 기능 구현

Sector별 작업 전에 다음 공통 기능을 먼저 준비한다.

---

## 9.1 Story 조건 기반 Target 활성화

조건에 따라 Target을 활성화할 수 있어야 한다.

예:

```text
FreezerHintRead == true
→ BasementKey Target 활성

KillerDiary3Read == true
→ Morgue Box B Special Interaction 활성
```

가능하면 Target GameObject 자체를 파괴하지 않는다.

체크포인트 복원 시 상태를 다시 계산할 수 있어야 한다.

---

## 9.2 일회성 Room Entry Event

특정 Room에 처음 들어왔을 때만 이벤트를 실행할 수 있어야 한다.

사용처:

- StartBedroom 퇴실 후 복도 이벤트
- Center Hallway 첫 진입
- Center Hallway 두 번째 구역 진입
- BasementCorridor 첫 진입
- Sector5 Entrance 도착

`PlayerRoomTracker`의 Room 변경 결과를 이용한다.

Trigger Collider를 별도로 남발하지 않는다.

---

## 9.3 Item Use Requirement

특정 Target이 Inventory Item 선택 UI를 요청할 수 있어야 한다.

결과는 최소 세 종류를 구분한다.

```text
CorrectItem
WrongItem
Cancel
```

필요하면 Empty Inventory도 별도 결과로 받을 수 있다.

사용처:

- NursingRoom 손전등
- Generator 퓨즈
- 열쇠가 필요한 문

---

## 9.4 Screen Shake

MachineRoom 기계 작동 시 사용할 간단한 화면 흔들림 기능을 준비한다.

현재 카메라 시스템을 먼저 확인한다.

Cinemachine 또는 기존 Camera Rig 기능이 있다면 그것을 활용한다.

별도 시스템이 없다면 현재 활성 Room Camera에 적용할 수 있는 가벼운 Screen Shake 컴포넌트를 만든다.

강도와 지속시간은 Inspector에서 수정 가능해야 한다.

---

## 9.5 Enemy Mode 전환

기존 Enemy AI를 활용하면서 최소한 다음 동작 모드를 구분할 수 있어야 한다.

```text
Inactive
ScriptedSequence
Patrol
Chase
```

Sector2의 살인마 이벤트에서는 `ScriptedSequence`.

Sector3/4에서는 `Patrol`.

Sector5에서는 `Chase`.

새 Enemy AI 전체를 만드는 것이 아니라 기존 AI의 목적지/상태 전환 기능을 활용한다.

# 10. Sector1 구현

## 10.1 게임 시작 Intro Target

`StartBedroom` 플레이어 시작 위치 바로 아래에 Story Target을 배치한다.

초기 활성 Target은 이것 하나뿐이다.

Target 선택 시:

```text
[게임 시작 무전기 대화]
```

를 Pause Dialogue로 실행한다.

Dialogue 완료 후:

```text
IntroDialogueCompleted = true
```

그 후 StartBedroom의 다음 Target들을 활성화한다.

- 출입문
- 조사 서랍
- 기타 이번 구간에서 필요한 Target

씬 전체 Target을 검색하지 않는다.

StartBedroom 내부 필요한 Target Root만 직접 참조한다.

---

## 10.2 StartBedroom 조사

양쪽 서랍에 조사 Target을 둔다.

둘 모두:

```text
아무것도 발견되지 않았다.
```

를 출력한다.

---

## 10.3 첫 복도 진입 이벤트

플레이어가 StartBedroom에서 처음 Hallway로 나왔을 때 일회성 이벤트를 실행한다.

복도 끝의 **Sector2 / Center Hallway 방향 문**이 닫히는 모습을 보여준다.

StartBedroom 출입문이 아니다.

문이 닫힌 뒤:

```text
[복도 끝 문이 닫히는 것을 본 주인공]
```

Pause Dialogue 실행.

완료 후:

```text
StartHallDoorScareSeen = true
```

이벤트는 다시 실행하지 않는다.

---

## 10.4 복도 끝 문

Sector1 진행 중 복도 끝 Sector2 방향 문을 선택하면:

```text
잠겨있다.
```

메시지를 출력한다.

병실 복도 열쇠 획득 전에는 이동할 수 없다.

---

## 10.5 FlashBedroom

### 옷장

조사 Target 추가.

결과:

```text
아무것도 발견되지 않았다.
```

### 서랍

ItemAcquired 계열 Target 추가.

획득:

```text
손전등
```

획득 후:

```text
FlashlightAcquired = true
```

손전등은 소비하지 않는다.

---

## 10.6 DiaryBedroom

지정 서랍에 MessageTarget을 둔다.

내용:

```text
[일기장 1번]
```

스토리상 병실에서의 살인마 일기.

실제 문구는 이후 사용자 검수 단계에서 입력한다.

# 11. NursingRoom 구현

## 11.1 기본 조명

NursingRoom 자체를 의도적으로 어둡게 유지한다.

방 내부 Story용 Spot Light를 하나 준비한다.

Spot Light는 플레이어 Transform을 따라다니며 플레이어 앞쪽을 비춘다.

기본 상태:

```text
Inactive
```

NursingRoom 밖에서는 항상 꺼진다.

---

## 11.2 최초 입장

`NursingRoomFlashlightActivated == false`인 상태에서 NursingRoom에 들어오면:

1. 방 진입
2. `[너무 어둡다]` Story Message
3. Item Use UI 강제 표시

Inventory가 비어 있어도 UI는 표시한다.

플레이어가 필요한 아이템을 추측할 수 있어야 하기 때문이다.

---

## 11.3 Item Use 결과

### 손전등 선택

```text
CorrectItem
```

처리:

- 손전등 소비하지 않음
- `NursingRoomFlashlightActivated = true`
- Spot Light 활성
- NursingRoom 서랍 Target 활성
- 플레이어는 NursingRoom에 그대로 남음

### 취소

7. Timeline 완료 이벤트 대기
8. Ending Credit 표시
9. Credit 종료 후 기존 Title 화면으로 복귀

## Timeline 연결

각 Ending은 선택적으로 `PlayableDirector`를 참조할 수 있게 한다.

```text
BadEndingDirector
HappyEndingDirector
```

현재는 Timeline Asset이 없어도 정상 동작해야 한다.

Director가 연결되어 있으면:

```text
Timeline 재생
→ stopped 이벤트
→ Credits
```

Director가 없으면:

```text
[Bad Ending 텍스트 대체본]
```

또는

```text
[Happy Ending 텍스트 대체본]
```

같은 임시 Ending 화면으로 진입할 수 있게 한다.

향후 실제 Ending Map / Timeline을 제작해도 Ending Target 코드를 다시 수정하지 않도록 한다.


자동 진행 또는 버튼 방식은 기존 UI 구조에 맞춘다.

Credits 완료 후 현재 프로젝트의 기존 Title 진입 방식을 사용한다.

# 43. GPT / Codex에게 작업을 넘길 때의 규칙

각 Phase를 한 번에 하나씩 작업한다.

다음 Phase로 넘어가기 전에 반드시 현재 Phase를:

```text
코드 컴파일
→ Console Error 확인
→ Scene Reference 확인
→ Play Mode 실행
→ 실제 진행 검증
→ Checkpoint Restart 검증
```

순서로 완료한다.

기존 Script를 수정하기 전에는 현재 구현을 먼저 읽는다.

기존 시스템의 책임을 파악하지 않고 동일 기능의 새 Manager를 추가하지 않는다.

씬 배치에서는 임시 `Find` 코드로 문제를 해결하지 말고 Serialized Reference 또는 현재 프로젝트에서 사용 중인 명시적 연결 방식을 사용한다.

특히 Story 진행 기능은 다음 세 데이터를 서로 혼동하지 않는다.

```text
물리적 GameObject 위치
PlayerRoomTracker가 판단하는 논리 Room
StoryProgress가 판단하는 진행 상태
```

Sector2 강제 복귀, Sector3/4 Enemy Room 이동, Sector5 Final Chase에서는 이 세 상태가 항상 일치하는지 검증한다.
